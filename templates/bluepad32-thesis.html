01 / Research background

A familiar controller.
A more accessible platform.

Dr Luigi Manfredi suggested developing a control platform for a medical robot. His existing endorobot setup used an Xbox controller with MATLAB/Simulink and Arduino Mega boards.

Dharshan explored that approach, but the MATLAB/Simulink environment was financially inaccessible to him. The block-based hardware configuration also appeared complicated for the simpler platform he wanted to investigate. This prompted a search for an affordable, straightforward wireless alternative while retaining the familiar gamepad interface.

Source: researcher-provided background. The existing setup was not benchmarked against this prototype; no comparative latency finding was established.

02 / Finding an alternative

Bringing wireless input onto the ESP32.

The ESP32 offered built-in Bluetooth, low-cost hardware and an Arduino IDE-compatible development route. It could receive gamepad input and interface with an external servo driver, making it a practical candidate for a compact control prototype.

The question became how to receive the Xbox controller's wireless input on the microcontroller, interpret it and pass useful commands to the motors. Bluepad32 provided the gamepad connection layer; the project supplied the application logic around it.

03 / Bluepad32 integration

From gamepad state
to a motor command.

Bluepad32 by Ricardo Quesada and contributors enabled the Xbox controller to communicate with the ESP32 over Bluetooth. The research contribution was integrating this existing library into the control prototype.

  1. Connect and read

    Connection callbacks track the gamepad's connection state. In the main loop, BP32.update() refreshes controller data. The application can then read buttons and joystick axes through the controller API, including axisRX() and axisRY().

  2. Filter and map

    The thesis applies a dead-zone threshold of 100 to the joystick axes to suppress small centre movements. Filtered values are mapped from the approximately −512 to +512 input range into constrained positional-servo targets, with direction inverted where required.

  3. Update and actuate

    A step-limiting routine moves the commanded angle towards its target in bounded increments. On an update flag, the ESP32 converts that command to PWM counts and sends it over I²C to the PCA9685. The driver supplies the servo pulses.

Command state is not shaft feedback.

The variable currentAngles stores the software's commanded state. Logging it does not independently measure the physical servo position or establish a closed-loop actuator feedback system.

Technical reference: thesis PDF pp. 24–39. Official Bluepad32 documentation ↗

04 / Servo motor experimentation

Testing the command chain.

The researcher's early trials used a 360-degree continuous-rotation servo to check controller-to-motor responsiveness. Appendix B identifies an FS90R continuous servo. This provided a way to observe a physical response to wireless input.

Initial trial · Author account

Continuous rotation

The pulse command primarily controls direction and speed around a neutral setting. It does not request an absolute shaft angle.

Thesis body · Chapters 4–5

Positional control

The thesis discusses MG996R servos, angular targets, PWM mapping and positioning tests. These measurements must be kept separate from the early continuous-servo trial.

For the positional-servo implementation, the PCA9685 generates the PWM output while the ESP32 calculates the target and limits command changes. The thesis describes a laser pointer and protractor method for checking final position. The motor used in each individual recording still needs to be confirmed from the original test records.

Technical reference: thesis PDF pp. 32–36, 45, 49 and 63. No motor model is inferred from the prototype photograph.

05 / Interrupts and responsiveness

The update clock and
the observation window.

The detailed timer implementation describes a short interrupt service routine that sets an update flag every 40 ms. The main loop handles the servo calculations and I²C writes when it sees that flag. Keeping the interrupt small lets gamepad processing continue between scheduled updates.

Configured interval

40 ms

Control update

Equivalent to 25 Hz. This schedules command updates; main-loop execution still affects when the work is serviced.

Logging interval

100 ms

Serial reporting

The described Serial Plotter stream reports controller values and commanded angles at approximately this interval.

These are different timing quantities. Neither interval alone establishes input-to-motion latency. Physical response also depends on wireless communication, processing, command transfer and the motor. Serial sampling limits what can be resolved from the plotted command stream.

Technical reference: thesis PDF pp. 25–28 and 39. The abstract and one smoothing discussion mention 10 ms; the detailed timer configuration specifies 40 ms. This inconsistency remains unresolved.

06 / Results and limitations

What the prototype demonstrates.

The thesis describes a working pathway from wireless gamepad input, through Bluepad32 and ESP32 control logic, to servo actuation. It combines input filtering, bounded command changes and serial monitoring in a compact experimental platform.

The numerical findings below are attributed to the thesis. They have not been independently reproduced for this webpage. Differences within the source are retained rather than silently reconciled.

Scope of the evidence

This is a medical robotics research control prototype. It is not a clinically validated endorobot, a completed surgical simulator or an independently validated force-feedback system. Chapter 5 identifies missing real-time force sensing, timing variation and inexpensive servo mechanics as limitations.

Open questions in the research record
  • Which servo and controller firmware were used in each run, and which update interval belongs to each recording?
  • How were 98 ± 12 ms timing values resolved from a stream described as reporting every 100 ms? Raw timestamps and the analysis method are needed.
  • Which angle-accuracy aggregate is correct, and what accounts for the step-response arithmetic difference?
  • The abstract mentions FSRs, potentiometer validation and clinician usability tests; the later limitations describe absent real-time force sensing and future validation. Their implementation and test records need confirmation.

The background account is supplied by the researcher. The four recordings and underlying datasets were not available for review.

Proposed future development

Measure the physical system, then extend it.

Further work would require independent position and latency measurement, actuator feedback, reliability testing and task-based evaluation. Chapter 6 proposes closed-loop control, ROS 2 integration and progressively more realistic validation environments. These remain future directions.
